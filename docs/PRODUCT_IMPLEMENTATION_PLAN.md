# Seoul Fit 제품 고도화 구현 계획

작성일: 2026-07-25
상태: 보류 기능을 제외한 로컬 구현·검증 완료 — 외부 연결 승인 대기
정본 범위: `seoul-fit-fe`와 `backend`의 제품 기능·데이터 계약

## 1. 제품 목표

Seoul Fit을 단순한 공공시설 마커 지도가 아니라 다음과 같은 생활 의사결정
서비스로 완성한다.

> 서울에서 지금 무엇을 할 수 있고 어디로 가는 것이 좋은지를 실시간
> 공공데이터로 판단해 주며, 중요한 변화는 먼저 알려주는 생활 의사결정 지도

우선 사용자는 서울에서 지금부터 30분~3시간 동안 이용할 장소나 활동을 찾는
시민과 방문객이다. 서비스의 핵심 흐름은 다음과 같다.

```text
유입 → 장소·상황 탐색 → 현재 조건 확인 → 장소 결정 → 길찾기·예약·전화·저장
     → 관심 장소·생활권 알림 → 재방문
```

## 2. 완료 범위

### P0 — 핵심 탐색 복구

- 백엔드 POI 검색 인덱스를 사용하는 통합 검색
- 검색 결과 선택 시 지도 이동, 카테고리 활성화, 마커 선택, 상세 열기
- `/places/{category}/{id}`에서 지도로 이동할 때 동일 장소 자동 선택
- 지도와 목록의 선택·필터·현재 영역 동기화
- 카테고리, 거리, 운영 중, 예약 가능, 실내, 혼잡도 필터
- 길찾기, 예약·공식 페이지, 전화, 저장, 공유 행동
- 데이터 출처, 기준 시각, 갱신 상태, 실시간 지원 범위 표시
- 탐색·상세·행동 퍼널 계측과 회귀 테스트

### P1 — 실시간 의사결정

- 위치 기준 날씨·대기질·혼잡도를 합친 `서울 지금` 카드
- `지금 갈 수 있는 곳`, `한산한 곳`, `비 오는 날`, `오늘 행사`,
  `따릉이로 갈 곳`, `더위를 피할 곳` 상황 프리셋
- 관심사·거리·운영·예약·신선도·혼잡·날씨 위험을 이용한 규칙 기반 적합도
- 추천 결과마다 근거와 데이터 기준 시각 표시
- 선택 장소의 주변 대안 3곳
- 실시간 도시데이터 비지원 지역과 오래된 데이터의 명시적 fallback

### P2 — 재방문 구조

- 사용자별 장소 즐겨찾기와 최근 본 장소
- 집 근처·회사 근처 등 사용자가 명시적으로 저장하는 관심 생활권
- 알림 구독 조건: 유형, 생활권, 요일·시간, 방해 금지, 최소 재알림 간격
- 초기 알림 유형:
  - 대기질·폭염·폭우
  - 따릉이 부족·포화
  - 관심 지역의 문화행사·예약 정보
- 알림 생성 이유와 관련 장소·지도 deep link
- 인앱 알림 읽음·해제·관련 장소 이동
- 외부 Push 연결 전까지 provider 중립적인 발송 상태와 구독 모델 유지

### P3 — 차별화

- 30분~3시간 시간 예산과 관심사에 맞는 2~3개 장소 활동 계획
- 거리와 예상 체류시간을 고려한 설명 가능한 계획 순서
- 정해진 의도와 필터를 추출하는 규칙 기반 자연어 검색
- 핵심 탐색·상세·오류·빈 상태의 한국어·영어 제공
- 키보드 탐색, 포커스, 명도 대비, 상태 안내 등 WCAG 2.2 AA 핵심 항목

## 3. 명시적 보류 범위

다음 기능은 이번 목표에 포함하지 않는다.

- AI 챗봇
- 자체 경로 탐색·내비게이션 엔진
- 사용자 리뷰·커뮤니티
- 사용자 가치와 무관한 데이터셋의 무분별한 추가
- 네이티브 모바일 앱
- 학습 기반 추천 모델

외부 Google Search Console·GA4·Cloudflare 콘솔 설정과 Push provider 연결은
코드·테스트·운영 문서가 완성된 뒤 사용자 승인 게이트에서만 수행한다.

## 4. 단계별 구현 계약

### 4.1 P0 데이터·UI 계약

통합 검색 결과는 최소 다음 값을 가진다.

```text
stable id, source id, category, name, address,
latitude, longitude, source updated time
```

프론트는 별도 브라우저 전용 POI 목록을 검색 정본으로 사용하지 않는다. 검색
Route Handler를 통해 백엔드 검색 인덱스를 조회하며, 지하철·따릉이처럼 백엔드
검색 인덱스에 없는 실시간 항목은 같은 응답 타입으로 병합한다.

장소 식별자는 아래 양쪽 진입에서 동일해야 한다.

```text
검색 결과 → 지도 Facility
공개 장소 URL → 지도 Facility
```

지도에서 장소를 바로 찾을 수 없으면 좌표로 이동한 뒤 현재 영역 데이터를
새로 읽고 한 번 재선택한다. 그래도 찾지 못하면 위치 이동은 유지하고 사용자에게
데이터 갱신 안내를 표시한다.

### 4.2 신선도 계약

모든 실시간 또는 주기 수집 데이터에는 다음 상태 중 하나를 부여한다.

- `live`: 원천 기준 정상 갱신 범위
- `recent`: 실시간은 아니지만 의사결정에 사용할 수 있음
- `stale`: 기준 시간을 초과하여 경고와 함께 표시
- `unknown`: 원천 기준 시각 또는 범위를 판단할 수 없음

UI는 `실시간`이라는 문구를 원천 갱신 시각이 있고 정상 범위일 때만 사용한다.
서울 실시간 도시데이터가 지원하지 않는 지역에는 서울 전역 실시간 값처럼
보이는 혼잡도·날씨 기본값을 만들지 않는다.

### 4.3 규칙 기반 적합도 계약

적합도는 0~100점 범위이며 개별 요소와 추천 이유를 함께 반환한다.

```text
관심사 일치       +0..25
거리              +0..20
현재 운영         +0..15
예약·이용 가능    +0..10
데이터 신선도     +0..10
상황 프리셋 적합  +0..20
혼잡·날씨 위험    -0..30
```

점수만으로 정보를 숨기지 않는다. 상위 이유 최대 3개와 감점 경고를 표시한다.
데이터가 없으면 중립 점수를 주고 `정보 없음`을 명시한다.

### 4.4 위치 개인정보 계약

- 현재 위치는 주변 탐색과 트리거 평가에만 사용한다.
- 이동 궤적을 저장하지 않는다.
- 생활권은 사용자가 명시적으로 저장한 중심 좌표·반경·라벨만 보관한다.
- 삭제 시 해당 생활권을 참조하는 알림 구독도 함께 비활성화한다.
- 분석 이벤트에는 좌표, 주소, 검색 원문, 사용자 식별자를 보내지 않는다.

### 4.5 알림 계약

- 알림 생성과 외부 전송 성공을 구분한다.
- 구독별 cooldown과 방해 금지 시간을 서버에서 적용한다.
- 같은 원인·장소·사용자에 대한 중복 알림을 억제한다.
- 알림에는 생성 이유, 데이터 기준 시각, 관련 장소 또는 생활권 deep link를 넣는다.
- 외부 provider가 없어도 인앱 알림은 정상 동작해야 한다.

## 5. 분석 계약

### 핵심 지표

주간 의사결정 완료 사용자 또는 동의된 익명 세션 수:

```text
길찾기 | 예약·공식 페이지 | 전화 | 저장
```

중 하나 이상을 수행한 주간 고유 사용자·세션을 센다.

### 핵심 퍼널

```text
page_view(home_map)
→ map_ready
→ discovery_started
→ facility_detail_viewed
→ facility_action_clicked | place_saved
```

### 추가 이벤트

| 이벤트 | 목적 | 허용 파라미터 |
|---|---|---|
| `filter_applied` | 탐색 조건 사용 | `filter_type`, `filter_value` |
| `recommendation_viewed` | 추천 노출 | `preset`, `category`, `reason_code` |
| `alternative_selected` | 대안 전환 | `category`, `reason_code` |
| `place_saved` | 의사결정 완료 | `category`, `entry_point` |
| `alert_subscribed` | 재방문 의도 | `alert_type`, `has_zone` |
| `alert_opened` | 알림 재방문 | `alert_type`, `destination_type` |
| `stale_data_exposed` | 신뢰성 방어 | `data_type`, `freshness_status` |
| `plan_created` | 활동 계획 가치 | `duration_bucket`, `stop_count` |

좌표, 주소, 검색 원문, 장소명, OAuth 식별자, 사용자 DB ID는 전송하지 않는다.

### 품질 방어 지표

- 검색 무결과율
- 검색 결과 선택 실패율
- 오래된 데이터 노출률
- 외부 API·Route Handler 실패율
- 알림 해지율과 중복 억제율
- 장소 행동까지 걸린 시간

## 6. 구현 순서와 게이트

각 단계는 아래 순서로 진행한다. 앞 단계의 필수 검증이 실패하면 다음 단계로
넘어가지 않는다.

### Gate P0

- 검색·공개 URL·마커에서 같은 장소가 선택된다.
- 검색 또는 공개 URL 유입 후 두 번 이내 행동으로 상세 CTA에 도달한다.
- 필터와 목록이 지도 영역·마커와 일치한다.
- 모든 CTA가 유효하며 분석 이벤트에 개인정보가 없다.
- 프론트 type-check, Jest, production build와 관련 E2E가 통과한다.

### Gate P1

- 여섯 상황 프리셋이 동일한 평가 엔진을 사용한다.
- 추천 이유와 신선도 상태가 표시된다.
- 실시간 데이터가 없거나 오래돼도 허위 정상값을 만들지 않는다.
- 평가 엔진 단위 테스트와 주요 조합 통합 테스트가 통과한다.

### Gate P2

- 즐겨찾기·생활권·구독의 소유권 검증과 삭제 연쇄가 동작한다.
- cooldown·방해 금지·중복 억제가 서버 테스트에서 검증된다.
- 외부 provider 없이 인앱 알림의 생성→목록→클릭→장소 이동이 완결된다.
- Flyway migration, backend 전체 테스트, frontend 전체 테스트가 통과한다.

### Gate P3

- 활동 계획이 시간 예산과 서울 좌표 범위를 지킨다.
- 자연어 입력이 허용된 규칙·필터만 생성하고 원문을 분석으로 보내지 않는다.
- 핵심 흐름의 한국어·영어 전환과 키보드 조작을 검증한다.
- 전체 production build와 접근성 자동 검사·수동 체크리스트를 통과한다.

## 8. 검증 및 릴리스 원칙

- 기능 묶음 단위로 테스트하고 단계 게이트에서 전체 회귀를 수행한다.
- 인증이 필요한 쓰기는 `userId` 요청값이 아니라 인증 주체를 소유권 기준으로 삼는다.
- 외부 URL은 허용된 `http`·`https`만 사용하고 새 창 링크는 opener를 차단한다.
- 서울 좌표와 검색 반경을 서버와 클라이언트 양쪽에서 검증한다.
- 새 테이블과 컬럼은 Flyway로만 반영한다.
- 로그에 좌표 원문, 알림 본문, 전화번호, 이메일, 토큰을 남기지 않는다.
- dev 검증을 통과한 뒤에만 prod 배포를 수행한다.
- 외부 콘솔·Push provider 연결은 모든 코드 게이트 뒤 별도 승인을 받는다.

### 2026-07-25 — Gate P0

- 백엔드 검색 인덱스와 지하철·따릉이 결과를 하나의 검색 타입으로 병합했다.
- 검색 또는 공개 장소 URL에서 좌표 검증 후 지도 이동, 카테고리 활성화, 마커 선택,

- 현재 지도 영역과 카테고리·거리·운영 중·예약·실내·혼잡 조건을 공유하는
  마커/목록 필터 엔진을 추가했다.
- 상세 패널에 카카오맵 길찾기, 예약/공식 URL, 전화, 링크 공유, 로컬 저장과

### 2026-07-25 — 최종 보안·구조 점검

- 사용자 프로필·관심사·즐겨찾기·생활권·구독은 요청의 `userId`가 아니라 JWT
  인증 주체를 소유권 기준으로 사용한다. 다른 사용자 ID를 넣은 요청은 403으로
  거부하는 회귀 테스트를 추가했다.
- OAuth는 state를 생성·세션 저장·1회 소비하고, 서버가 provider의 일회용
  authorization code를 교환하는 흐름만 남겼다. 클라이언트가 보낸 OAuth ID로
  토큰을 발급하던 엔드포인트와 미사용 호환 코드·테스트를 제거했다.
- refresh token은 query string이 아닌 전용 header로 받고 access token을
  refresh token으로 사용할 수 없도록 타입을 검증한다.
- 운영 프로필은 admin·Prometheus·scheduledtasks를 공개하지 않는다. 위치
  요청은 서울 좌표·반경을 검증하고 트리거 기록에는 이동 좌표를 저장하지 않는다.
- 마커 HTML의 공공데이터 문자열을 이스케이프하고 외부 링크를 `http/https`로
  제한했으며 opener를 차단했다. 브라우저 날씨 비밀키, 좌표·OAuth code·토큰·
  개인정보 로그 경로를 제거했다.
- 프로덕션에서 데이터 암호화 키가 없으면 시작을 거부하고, 키 값 또는 일부를
  로그에 남기지 않는다.
- Pages Router `/home`에도 App Router와 같은 인증·분석·다국어 provider를
  적용했고, 사용되지 않던 레거시 인증 계층을 제거했다.
