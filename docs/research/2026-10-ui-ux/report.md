# 서울핏을 포트폴리오로 바꾸는 4단계 리디자인 계획

서울핏의 진짜 문제는 "덜 예쁜 것"이 아니라 **핵심 흐름이 끊겨 있는 것**이다. 2026-10-11 라이브 감사는 결함 **32건(P0 4·P1 10·P2 14·P3 4)**을 확인했고, P0 네 건 — 검색 제안이 지하철역·따릉이만 내놓는 것, 날씨·혼잡도 API가 502라 "서울 지금"이 네 군데서 각기 다른 실패 문구를 뿌리는 것, 모바일에서 접을 수 없는 탐색 패널이 지도의 **65%**를 덮는 것, 지도 컨트롤 3종이 탭조차 안 되는 것 — 은 색이나 폰트를 바꿔도 사라지지 않는다 ([라이브 감사](./live_site_ux_audit.md)). 코드 감사 두 건은 그 뒤에서 **동작하지 않는 버튼(현재 위치·날씨 새로고침), UI에 연결되지 않은 상태(로딩·부분 실패·권한 거부), 두 벌씩 존재하는 마커 파이프라인·색 정의·사이드바**를 찾았고, 스택 수준에서는 Tailwind 3.4 위에 shadcn **v4 세대 프리미티브**와 v4 전용 `tw-animate-css`가 얹혀 애니메이션·그림자·outline 유틸리티가 **조용히 0건 생성**되는 불일치를 두 노트가 서로 독립적으로 측정했다 ([셸 감사](./code_audit_shell_pages.md), [인터랙션 조사 §6.1](./map_interaction_patterns_libraries.md)). 그래서 순서는 **위생(스택 정합·잔재 제거) → 핵심 흐름 복구 → 토큰·타이포·다크모드 → 쇼케이스**이며, 디자인 방향은 Google·Naver·Kakao 지도의 유틸리티 골격에 Pretendard와 색 2개(한강 블루 primary `hsl(207 92% 38%)`, 2024 서울색 스카이코랄 계열의 live 액센트), **글리프가 필수인 9색 카테고리 체계**를 얹는 "한강 블루 유틸리티"로 고정한다. 라이브러리는 `@base-ui/react` Drawer(모바일 시트, 비모달·3단 스냅을 헤드리스 Chromium에서 실측)·`cmdk`·`sonner`·`next-themes`·`tailwindcss-animate`만 추가하고 `vaul`·`motion`·`react-kakao-maps-sdk`·`tw-animate-css`는 피하거나 걷어낸다. 포트폴리오 층은 평가자가 3초 안에 보는 결함(영문 쿠키 모달·기본 404·두 번씩 나오는 목록·콘솔 에러·옛 Vercel 링크)부터 지우고, README·`/about`·측정 조건이 붙은 품질 표·ADR로 "결정을 설명할 수 있는 증거"를 만든다. 전체 규모는 이 보고서 추정으로 약 **9–14 작업일**이며, 위생 반나절과 핵심 흐름 복구 3–5일이 체감 효과의 대부분을 낸다.

> **근거와 한계.** 이 계획은 같은 폴더의 조사 노트 6건(라이브 UX 감사, 지도 코어 코드 감사, 셸·보조 페이지 코드 감사, 디자인 방향·레퍼런스, 인터랙션 패턴·라이브러리, 포트폴리오 프레젠테이션)을 종합했다. 라이브 관찰은 모두 **헤드리스 Chromium(390/768/1440, 로그인 없음, 위치 권한 거부 상태)**이고 실기기·스크린리더·`next build` 산출물 검증은 없다. 코드 인용은 리비전 `da98ea5` 기준 `경로:라인`이다. 노트끼리 결론이 다른 지점은 **측정값을 추론보다 우선**했고 본문에서 그 사실을 명시한다. 루트 `test-kakao-map.html:10`에는 카카오 JS 키가 평문으로 들어 있는데, 이 보고서는 값을 기재하지 않는다.

## 라이브 결함 32건 중 P0 4건은 색이 아니라 흐름이 끊긴 문제다

라이브 감사는 Python Playwright로 6단계 스크립트를 돌려 **스크린샷 135장**과 DOM 측정값을 남겼고, 결론을 "기능 목록은 길지만 어느 하나도 끝까지 매끄럽지 않다"로 요약했다 ([라이브 감사 §5](./live_site_ux_audit.md)). 심사자가 3분 안에 느낄 미완성 신호는 다섯 가지다. 첫째, **핵심 차별점이 죽어 있다**: `/api/weather`·`/api/congestion`이 HTTP 502를 돌려주어 날씨 패널·혼잡도 패널·탐색 패널의 "서울 지금" 카드·상세 시트 확장 영역이 각기 다른 문구("연결 실패", "이 위치의 실시간 도시데이터를 확인할 수 없어…", "기준 시각 미확인", "혼잡도 정보를 불러올 수 없습니다")로 실패를 반복해 제품 전체가 '데이터 없음' 톤이 된다 ([seoulfit.damecasol.com](https://seoulfit.damecasol.com/), [스크린샷 desktop-weather-panel.png](./screenshots/desktop-weather-panel.png)). 상세 시트의 확장 영역은 백엔드가 살아나도 **항상** 실패를 보여주는데, `FacilityBottomSheetWrapper.tsx:53-65`가 `weatherData`·`congestionData` prop을 넘기지 않고 시트는 `propCongestionData`/`propWeatherData`만 읽기 때문이다(`FacilityBottomSheet.tsx:763-791, 802-833`; 실제 데이터는 `MapView.tsx:142-162`의 훅 안에만 존재) ([지도 코어 감사 D-03](./code_audit_map_core.md)).

둘째, **검색이 체험을 배신한다.** placeholder는 "한산한 실내 도서관"을 권하지만 "도서관"을 치면 자연어 옵션 하나와 따릉이 대여소 10건("349. 어린이도서관"…)만 나오고, 실제 도서관명 "개봉도서관"은 0건, "서울도서관"은 따릉이 3건이다. 서버 `/api/search/index`에는 **30,204건**(무더위쉼터 8,184·음식점 6,432·문화행사 5,035·도서관 216·공원 133)과 "…도서관" 1,072건이 있는데 제안에 전혀 반영되지 않으므로 `src/shared/lib/hooks/useSearchCache.ts`의 refTable/refId 병합 단계가 의심된다(콘솔 에러 없음, 정확 원인 미확인). 초성 퍼지 매칭(`getMatchScore` 50/40점)은 "남산"→낙성대·별내역·구리역(경기도), "여의도"→오이도역·시청.용인대역 같은 오탐을 만든다. Enter는 검색이 아니라 자연어 규칙을 적용해 "현 지도 0곳·필터 1"의 빈 지도를 만들고 목록을 자동으로 열며, 검색창 X로 지워도 규칙이 그대로 남는다(`Header.tsx`의 onKeyDown이 첫 option에만 포커스를 옮기고, 규칙 적용이 `onSearchClear`와 분리됨) ([라이브 감사 #2·#9](./live_site_ux_audit.md), [desktop-search-exact-library.png](./screenshots/desktop-search-exact-library.png)).

셋째, **모바일에서 지도가 보이지 않는다.** 390×844에서 탐색 패널(366×533, y133–666)이 지도 영역 65%를 덮고 접는 수단이 없다 — `PlaceExplorerPanel.tsx:122-125`의 `absolute left-3 right-3 top-14 max-h-[calc(100%-7rem)]` 고정 오버레이에 모바일 분기가 없다. 혼잡도(326,93)·날씨(16,700)·현재 위치(326,700) 버튼은 `elementFromPoint` 기준 **모두 탭 불가**다: 혼잡도는 전폭 칩 행 컨테이너(`MapView.tsx:714` `left-3 right-3 top-3 z-30`)의 빈 영역이 포인터를 가로채고, 나머지 둘은 같은 `z-30`이면서 DOM상 뒤에 오는 패널이 덮는다(`MapControls.tsx:115,150,182`). 데스크톱도 패널 하단(y835–844)이 날씨 버튼(y772–820)을 덮어 Playwright 클릭이 거부됐다 ([라이브 감사 #3·#4](./live_site_ux_audit.md), [mobile-controls-occlusion-check.png](./screenshots/mobile-controls-occlusion-check.png)). 셸 감사는 같은 겹침을 좌표 산술로 독립 도출했다(`main` 높이 772px → 패널 y≈56–716, 지도는 하단 56px만 노출) ([셸 감사 D02](./code_audit_shell_pages.md)).

넷째, **추천·프리셋·플래너가 데이터와 따로 논다.** 기본 위치에서 프리셋 6종이 전부 같은 세 지하철역(시청역·시청역·을지로입구역)을 점수만 바꿔(57/53/69/49/49/63) 내놓고, "오늘 행사"·"따릉이로"는 행사·대여소를 하나도 보여주지 않으며 "비 오는 날"은 지하철역을 "실내에서 이용할 수 있어요"로 추천한다. 원인은 `src/features/recommendation/lib/recommendation-engine.ts:133-146`이 **이미 로드된 시설만 재채점**하고 카테고리를 활성화하지 않는데 기본 활성 카테고리가 `usePreferences.ts`의 park·subway뿐이라는 점이다. 강남구로 이동해도 추천은 시청 기준이고, 활동 계획은 같은 역을 두 번(모바일은 세 번) 방문한다 — 환승역이 호선별 별개 레코드로 존재하기 때문이다 ([라이브 감사 #6·#7·#8·#32](./live_site_ux_audit.md), [desktop-activity-plan-result.png](./screenshots/desktop-activity-plan-result.png)). 같은 화면에 "현 지도 375곳" vs 하단 필 "372개 시설" vs 칩 "132"처럼 집계 기준이 세 개인 것도 같은 뿌리다(`MapStatusIndicator.tsx:59-64`는 마커 오버레이 수, `PlaceExplorerPanel.tsx:130`은 뷰포트 시설 수, `MapView.tsx:717` 칩은 전역 로드 수) ([지도 코어 감사 D-15](./code_audit_map_core.md)).

다섯째, **마감 디테일이 기본값 그대로다.** 첫 방문마다 Cloudflare Zaraz의 영문 혼용 쿠키 모달("analytics — Anonymous page and feature usage analytics.", 시스템 폰트, 파란 버튼 3개)이 화면 전체를 블러 처리하고, 그 전에 SSR 랜딩(`HomeLanding`)이 0.3초 보였다가 지도로 통째로 교체되는 플래시가 있다(`app/page.tsx:20-22`의 Suspense fallback이 서버 HTML이 되는 이유는 `MapContainer.tsx:120`·`MapView.tsx:85`의 `useSearchParams()` CSR bailout). 존재하지 않는 URL은 Next 기본 영문 404(`app/` 루트에 `not-found.tsx`·`error.tsx`·`loading.tsx` 없음), `/profile`은 비로그인 시 안내 없이 즉시 `/`로 튕기고, `/auth/callback`은 ❌ 이모지와 3초 자동 이동이다. 공개 목록 `/places/library`는 **모든 항목이 두 번씩**(4.19혁명기념도서관×2…, "총 432곳"은 인덱스 216건의 정확히 2배) 나오고 "[페관] 송중문화정보도서관" 같은 폐관 시설·오타, 무더위쉼터 카드의 원시 태그 "특정계층이용시설,회원이용시설", 문화행사 "총 8,000곳"이 그대로 노출된다(`src/shared/lib/seo/public-places.ts`의 `getPublicPlacePage`, 중복 원인 미확인). 시트의 드래그 핸들은 왼쪽 정렬에 열릴 때 파란 포커스 사각형이 보이고, 데스크톱에서는 1440px 전폭 시트에 액션 버튼 4개가 342px씩 늘어난다. 상단 칩은 숫자만("132", "784") 보여주고 공원 아이콘은 경고 삼각형처럼 읽히며, 다크모드는 `prefers-color-scheme: dark`에도 전부 라이트이고, 모바일에는 언어 토글·'장소 둘러보기' 진입로가 없다(`Header.tsx:594,651` `hidden sm:inline-flex`, 사이드 메뉴에도 없음) ([라이브 감사 #5·#10·#15·#16·#18·#20·#24](./live_site_ux_audit.md), [mobile-places-library-page2.png](./screenshots/mobile-places-library-page2.png)).

코드 감사는 라이브에서 보이지 않던 "죽은 배선"을 추가로 찾았다. 우하단 **현재 위치 버튼은 아무 일도 하지 않는다**: `MapContainer.tsx:319`가 `<MapView />`를 props 없이 렌더해 `MapView.tsx:666`의 폴백 `() => {}`가 버튼에 연결되고, `MapProvider.tsx:144-146`의 `moveToCurrentLocation`은 정의부 외 참조 0건이다. **날씨 새로고침도 무동작**이다: `MapView.tsx:707`이 `refreshWeatherData`를 인자 없이 넘겨 `useWeather.ts:71-73`에서 위치가 없으면 즉시 return하는데, 혼잡도 쪽(`:686`)은 `() => refreshCongestionData(currentLocation)`로 올바르다. 첫 3–5초의 빈 지도에 로딩·실패 안내가 없는 이유는 `FacilityProvider.tsx:523-550, 765`의 통합 `loading`/`error`를 `MapView.tsx:89-99`가 구독하지 않고 `useFacilities.ts:24-26`이 빈 배열 stub이라 `error`가 항상 null이기 때문이며, 소스별 fetch 실패는 `console.error`로 삼켜진다(`FacilityProvider.tsx:218-286`). 지역 바로가기·검색으로 다른 동네로 가면 공원·도서관(전역 로드)만 보이는 이유는 위치 기반 8개 소스 로드(`loadLocationBasedData`, 반경 2km, `FacilityProvider.tsx:181-205`)가 최초 geolocation 성공 시 한 번만 호출되고(`MapView.tsx:581`) `handleRegionSelect`(`:453-473`)·`revealFacility`(`MapContainer.tsx:133-151`)는 panTo만 하며, 이후 `updateLocation`은 0.3km 이내면 스킵(`:725-730`)하기 때문이다. 지하철 요청은 좌표가 시청으로 하드코딩돼 있고(`useSubwayStations.ts:59`) 첫 로드에 20KB가 두 번 나간다. `useLocation.ts:161-189, 248-256`의 `watchPosition`이 콜백마다 `setCenter`를 호출해 모바일에서 지도를 손으로 옮겨도 GPS 갱신 때마다 되돌아가고, `MapView.tsx:571`의 별도 `getCurrentPosition`과 합쳐 지오로케이션 세션이 두 개다. 현재 위치 파란 점은 `MapView.tsx:619-623`의 객체 리터럴이 매 렌더 새 참조라 `useCurrentLocationMarker.ts:160-164`의 effect가 재실행되어 펄스가 깜빡이며 리셋되고, 권한 허용 전에도 시청 좌표(`FacilityProvider.tsx:172-176`)에 찍힌다 ([지도 코어 감사 D-01·D-02·D-04·D-05·D-06·D-13](./code_audit_map_core.md)).

레이어 체계는 숫자 체계가 아니라 **DOM 순서에 기대 우연히 동작**한다. 시설 시트 overlay `z-40`(`FacilityBottomSheet.tsx:328`)은 sticky 헤더 `z-50`(`MainApp.tsx:84`) 아래라 `aria-modal` 다이얼로그가 열린 채 헤더 검색창이 밝고 클릭 가능한 반면, 클러스터 시트는 `fixed inset-0 z-50`(`ClusterBottomSheet.tsx:99`)로 헤더까지 덮어 둘이 다르다. 같은 `z-30`에 절대 배치 요소 7개(칩 행·컨트롤 3·상태 표시 2·탐색 패널)가 서로의 영역을 가정하지 않고, 토스트 9999·skip link 100·로그아웃 80/70·사이드바 60/59·마커 998–1002는 토큰 없는 매직 넘버다 ([지도 코어 감사 §2.4](./code_audit_map_core.md), [셸 감사 §1](./code_audit_shell_pages.md)). 마커의 hover/선택 상태는 `element.style.zIndex`만 바꾸는데(`useMapMarkers.ts:219-226, 350-368`) Kakao `CustomOverlay` 래퍼가 `position:absolute + z-index`로 자체 쌓임 맥락을 만들어 **효과가 없다** — 지도 코어 감사는 이를 "재현 추론"으로 표시했고, 인터랙션 조사가 실험 E3에서 `overlay.setZIndex()`만 순서를 바꾼다는 것을 실측해 확인했다. `highlightMarker`는 호출처 0건, `.marker-selected`는 어디서도 적용되지 않는다 ([지도 코어 감사 D-12](./code_audit_map_core.md), [인터랙션 조사 §2.2](./map_interaction_patterns_libraries.md)).

## Tailwind 3.4 위의 v4 프리미티브가 애니메이션과 그림자를 0건으로 만들었다

이 발견은 두 노트가 **서로 독립적으로 측정**했기 때문에 가장 확실한 축이다. 셸 감사는 Tailwind 3.4.19 CLI로 `app/globals.css`를 그대로 컴파일해 `.shadow-xs`, `.outline-hidden`, `.rounded-xs`, `.animate-in`, `.fade-in-0`, `.zoom-in-95`, `.slide-in-from-*`, `.max-h-(--radix…)`, `.origin-(--radix…)`, `.has-data-*`가 **모두 0건** 생성되고, `tw-animate-css`의 `@theme inline`/`@utility` 블록 **51개**가 CSS에 원문 그대로 통과(브라우저는 무시)하는 것을 확인했다. 같은 빌드에서 `.hover\:bg-primary\/90`, `.size-9`, `.has-\[\>svg\]`, `.text-\[11px\]`, `.z-\[59\]`는 정상 생성됐으므로 파이프라인 자체가 아니라 **v4 전용 문법**이 문제다 ([셸 감사 §0.1·§2](./code_audit_shell_pages.md)). 인터랙션 조사는 별도 테스트 프로젝트(실험 E9)에서 설치본 `tw-animate-css@1.3.6`가 `animate-in slide-in-from-left-5 fade-in-0 data-[state=open]:animate-in`을 0건 생성하고, 같은 스캔에 `tailwindcss-animate@1.0.7`(peer `tailwindcss >=3.0.0`)을 플러그인으로 붙이면 `.animate-in`·`slide-in-from-left-5`·`fade-in-0`·`data-[state=open]:animate-in`·`slide-out-to-bottom`·`zoom-in-95`가 전부 생성되며 v3 문법 `max-h-[--radix-dropdown-menu-content-available-height]`도 생성됨을 확인했다 ([인터랙션 조사 §6.1](./map_interaction_patterns_libraries.md)). shadcn 문서는 "We've deprecated `tailwindcss-animate` in favor of `tw-animate-css`"라고 쓰지만 그 문맥은 Tailwind v4 신규 프로젝트이고, 같은 문서가 "Your existing apps with Tailwind v3 and React 18 will still work"라고 명시한다 ([shadcn Tailwind v4](https://ui.shadcn.com/docs/tailwind-v4)).

영향은 눈에 보이는 "뚝 끊기는 열림"보다 넓다. `dropdown-menu.tsx:36,204`, `sheet.tsx:33,55-63`, `CongestionPanel.tsx:27`, `WeatherPanel.tsx:26`, `FacilityBottomSheet.tsx:754`의 enter/exit 애니메이션은 CSS가 없어 무동작이고, `button.tsx:12-17`·`switch.tsx:13`의 `shadow-xs`가 생성되지 않아 **버튼·스위치에 그림자가 없다.** 드롭다운 항목의 `outline-hidden`이 생성되지 않아 브라우저 기본 outline과 전역 `:focus-visible` outline이 이중으로 보이고, `max-h-(--radix…)`가 없어 드롭다운의 가용 높이 제한이 사라진다. `alert.tsx:7`의 `calc(var(--spacing)*4)`는 v3에 `--spacing`이 없어 아이콘 열이 `grid-cols-[0_1fr]`로 떨어져 아이콘과 본문이 겹친다. 프리미티브 세대도 섞여 있다 — `input.tsx`·`checkbox.tsx`만 v3 세대(forwardRef, `h-10`, `ring-offset-background`)이고 나머지는 v4 세대라 버튼 `h-9`과 인풋 `h-10`의 높이가 다르고 포커스 링 언어(2px+offset vs 3px 반투명)가 나란히 노출된다(`EngagementPanel.tsx:338-369`). 설치된 `tailwind-merge`는 3.3.1인데 README는 "if you use Tailwind v3, use tailwind-merge v2.6.0"을 명시하고 ([tailwind-merge README](https://github.com/dcastil/tailwind-merge)), `components.json`의 `"tailwind": {"config": ""}`는 문서상 "For Tailwind CSS v4, leave this blank"이므로 지금 `shadcn add`를 실행하면 계속 v4 레지스트리를 가져온다 ([shadcn components.json](https://ui.shadcn.com/docs/components-json)).

여기서 노트 간 충돌 하나를 명시적으로 해소한다. 지도 코어 감사 D-11은 시트 등장 애니메이션을 "`data-state`+`tw-animate-css`(이미 import됨: `app/globals.css:1`)로" 구현하자고 제안했다. 이 제안은 코드 읽기 기반 추론이고, 위 두 측정과 정면으로 모순된다. **측정을 따른다: `tw-animate-css`는 패키지와 `globals.css:1`의 import를 제거하고 `tailwindcss-animate@1.0.7`을 `tailwind.config.js` plugins에 넣는다.** 한계도 함께 적는다 — 두 측정 모두 Tailwind CLI 출력 단계까지이며 `next build` 산출 CSS와 브라우저 렌더는 확인하지 않았다. 다만 Next도 같은 `postcss.config.mjs`(tailwindcss + autoprefixer) 파이프라인을 쓰므로 결과가 달라질 이유가 없고, 0단계에서 빌드 후 `.next/static/css`에 `.animate-in`이 존재하는지 grep 한 번으로 닫는다.

v3 유지냐 v4 전환이냐는 결정이 필요하다. 셸 감사는 "(a) v4 전환이 현재 프리미티브와 정합"이라고 평가했지만, 이 보고서는 **Tailwind 3.4 유지**를 택한다. 이유는 세 가지다. 첫째, 디자인 노트의 토큰(HSL 삼중값 + `theme.extend`, 모든 텍스트 쌍 대비 검산 완료)과 인터랙션 노트의 모든 스케치 클래스(`aria-[pressed=true]:`, `data-[swiping]:`, `[mask-image:…]`, `overscroll-x-contain` 등)가 **3.4.19에서 생성 확인된 상태**라 v4로 가면 이 검증을 통째로 버리게 된다. 둘째, v4의 preflight 변경과 Kakao SDK가 주입하는 DOM의 상호작용은 어느 노트도 평가하지 않았다(셸 감사 Gaps 명시). 셋째, 고장의 실체는 v4 전용 유틸리티 약 11종뿐이라 손으로 번역하는 비용이 반나절이다. 번역 표: `shadow-xs → shadow-sm`, `outline-hidden → outline-none`, `rounded-xs → rounded-sm`, `max-h-(--radix-x) → max-h-[var(--radix-x)]`, `origin-(--radix-x) → origin-[var(--radix-x)]`, `has-data-[slot=card-action] → has-[[data-slot=card-action]]`, `@container/card-header`는 제거, `calc(var(--spacing)*4) → 1rem`, `input`·`checkbox`는 `h-9`와 `focus-visible:ring-[3px] focus-visible:ring-ring/50`으로 통일해 세대를 맞춘다. `components.json`의 `tailwind.config`에 `"tailwind.config.js"`를 채워 이후 생성물이 v3 출력이 되게 하고, v4 전환은 별도 ADR(`docs/decisions/`)로 미룬다. `tailwind-merge`는 2.6.0으로 내린다.

## 디자인 방향은 "한강 블루 유틸리티": 색 2개, Pretendard 1종, 글리프 필수 9색 카테고리

디자인 노트가 실제로 열어 본 지도 제품은 모두 "밝은 지도 타일 + 흰색 solid 표면 + 단일 브랜드 색 + 카테고리 색 마커"를 공유한다. Kakao Map 데스크톱은 좌측 ~280px 패널의 검색창 **바로 아래에 현재 동네 + 날씨·미세먼지 한 줄**을 두고 지도 위 상단에 흰 pill 카테고리 칩, 우측에 컨트롤 열을 둔다(모바일 `m.map.kakao.com`은 403으로 미확인). Naver Map은 좌측 아이콘 레일 + 300px 패널, 상단 칩, 우상단 지도유형 세그먼트이고 모바일은 흰 헤더 + 연회색 둥근 검색 필드 + 하단 카드다. Google Maps는 좌측 72px 레일 + 검색 pill, POI는 **원형 색 배경 + 흰 글리프**, 다이얼로그는 scrim 위 solid 흰색이다. Airbnb 2025 앱(Newsroom 공식 이미지 4장)에서는 큰 pill 검색과 날짜 배지 타임라인 카드만 가져오고 3D 아이콘·사진 의존은 공공 데이터 유틸리티에 맞지 않아 배제한다 ([디자인 노트 §1](./design_direction_references.md), [Airbnb Newsroom](https://news.airbnb.com/product-releases/airbnb-2025-summer-release/)). Apple HIG Maps는 정보가 많은 콘텐츠를 지도 위에 돋보이게 하려면 muted 강조를, 커스텀 컨트롤에는 얇은 stroke나 약한 drop shadow로 지도와 대비를 주라고 권한다 ([Apple HIG Maps](https://developer.apple.com/design/human-interface-guidelines/maps)). 한국어 가독성 수치는 KRDS가 제공한다: 본문 17px(최소 16px), 행간 150% 이상, 굵기 400/500/700 ([KRDS 타이포그래피](https://www.krds.go.kr/html/site/style/style_03.html)). 현재 서울핏은 강조색이 남색 로고(`bg-[#0F284E]`, `Header.tsx:342`)·파랑 필터·초록 칩·보라 추천 4종으로 분산되고, 한국어 웹폰트가 없으며(`globals.css:8-9` `--font-geist-sans: Arial, Helvetica` 변수는 소비처 0, 실제 본문은 Tailwind preflight 기본 `ui-sans-serif, system-ui`), 포커스 링은 `#2563eb` 하드코딩이다.

**결정: "한강 블루 유틸리티."** A형(Google/Naver/Kakao 유틸리티 골격) 위에 KRDS 수치와 Airbnb의 극히 일부(검색 pill, 플래너 타임라인 카드)만 얹고, 서울 정체성은 색 2개와 Pretendard 타이포로만 표현한다. primary `hsl(207 92% 38%)`(#086ABA)는 서울시 대표 10색의 '서울하늘색(SC7909)'과 2024~2026 서울색이 하늘·강·빛에서 추출된다는 공식 체계를 **참조**하되 로고·상징색 값을 복제하지 않는다(2008 10색의 RGB는 공개 페이지에 없음). live 액센트 `hsl(347 88% 46%)`(#DD0E3B)는 2024 서울색 스카이코랄 sRGB(248,73,108)의 계열이고, 스카이코랄 원색(`--live-brand` #F8496C)은 흰 글자 대비가 3.41:1이라 점·그라디언트·대형 숫자 장식에만 쓴다 ([서울시 올해의 서울색](https://www.seoul.go.kr/seoul/color.do)). Toss Blue `#0064FF`(hsl 217)·Naver 초록·Kakao 노랑·Google 파랑과 색상각이 다르다는 점도 확인했다 ([Toss 브랜드](https://brand.toss.im/)). 큰 면적의 단일 브랜드색(Citymapper식)은 9개 카테고리 마커·상태색과 충돌하고, Airbnb식 소프트 톤은 사진 자산이 없는 서비스에서 "장식"으로 읽혀 기각했다. 소유자는 "그럴듯하고 멋지게"로 선택을 위임했으므로 이 결정에 재승인을 요구하지 않는다 ([디자인 노트 §2·§3](./design_direction_references.md)).

### 토큰: shadcn HSL 관례를 유지하고 상태·카테고리·엘리베이션·모션을 추가한다

### 타이포그래피: Pretendard Variable 동적 서브셋, 본문 15px, 굵기 4단계

후보 네 종을 fontTools로 실측한 결과 **Pretendard 1.3.9**(OFL-1.1)와 Wanted Sans만 한글 11,172자 전체를 담는다. Wanted Sans는 wght 하한이 400이라 캡션용 가벼운 굵기가 없고, SUIT는 2,668자라 공공 장소명(동적 데이터)에서 글리프 폴백이 섞이며, Noto Sans KR은 라틴 폭이 넓어 UI에서 기본값처럼 보인다. Pretendard는 Inter 기반 라틴·`tnum`(표 숫자)·`case`·`ss01~16`을 지원하고 npm 패키지에 **dynamic subset CSS + 92개 woff2 조각**(조각당 8–44KB)이 들어 있어 CDN 없이 셀프호스팅할 수 있다. 서울핏의 한국어 UI 문구(`messages.ts` + 소스 내 한글, 고유 음절 443자)는 92조각 중 **18조각 ≈ 482KB**만 요구하고 장소명 같은 동적 텍스트는 등장 시 12–18KB 조각만 추가로 받는다. 가변 전체 파일은 **2,057,688B(≈2.06MB)**라 `next/font/local`로 통째로 preload하면 안 된다 ([디자인 노트 §5](./design_direction_references.md), [Pretendard](https://github.com/orioncactus/pretendard)). 로딩은 **A안: `app/layout.tsx`에서 `pretendard/dist/web/variable/pretendardvariable-dynamic-subset.css`를 import**하고, CLS 완화용 폴백 `@font-face 'Pretendard Fallback'`(`local('Apple SD Gothic Neo')` 등, `ascent-override: 95.2%; descent-override: 24.1%` — hhea 메트릭 실측)을 `globals.css`에 둔다. 이 리포에서 빌드해 `.next/static/media`에 조각이 생성되는지와 Turbopack 처리 방식은 **미검증**이므로 구현 시 1회 확인하고, 실패하면 `public/`에 조각을 복사하는 경로로 간다. Docker standalone은 `public`과 `.next/static`을 `standalone/`에 직접 복사해야 한다 ([Next.js output](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)). 서울서체(한강체·남산체)는 서울시 두 공식 페이지의 공공누리 유형이 1유형과 4유형으로 **상충**해 웹폰트 서브셋·임베딩 허용 여부가 불명확하고 디스플레이 서체라 본문에 부적합하므로 제외한다 ([서울서체](https://www.seoul.go.kr/seoul/font.do), [문화분야 안내](https://news.seoul.go.kr/culture/archives/529602)).

스케일은 `display` 28/36(데스크톱 32/40, -0.01em, 700) · `title` 20/28(700, 장소명·시트 제목) · `section` 17/24(600) · `body` 15/22 · `body-sm` 14/20 · `label` 13/18(500, 칩·배지) · `caption` 12/16(메타 전용, 최소)이며 굵기는 400/500/600/700 네 단계로 제한한다. Pretendard의 x-height는 1086/2048≈0.53em으로 Inter와 같아 15px 본문이 KRDS의 17px(Pretendard GOV 기준)보다 작아도 되지만 **본문 하한 15px, 터치 가능한 레이블 13px, 메타 12px 미만 금지**로 둔다. 현재 `text-[11px]` 임의 크기 7곳(`PlaceExplorerPanel.tsx:248,262,363,430`, `ActivityPlanner.tsx:75,134,146`)은 `caption`으로 올린다. `body { word-break: keep-all; overflow-wrap: anywhere; }`로 한글 어절 단위 줄바꿈과 긴 영문 토큰 강제 분리를 함께 보장하고 ([MDN word-break](https://developer.mozilla.org/en-US/docs/Web/CSS/word-break)), 시간·거리·대수·점수는 `tabular-nums`로 정렬한다(별도 모노 폰트 불필요). 이탤릭은 Pretendard에 없으므로 합성 기울임을 막고, 메타 구분자는 ` · ` 가운뎃점, 단위는 `1.2km`·`3분`·`17°`처럼 붙여 쓴다 ([디자인 노트 §9](./design_direction_references.md)).

### 카테고리 체계: 9색은 보조 신호이고 글리프·라벨·숫자가 1차 신호다

### 표면·다크모드·모션 규칙 — 그리고 다크 지도에 관한 충돌 해소

텍스트가 있는 표면(카드·시트·목록·토스트·다이얼로그·마커 라벨)은 **solid**, 지도 위 컨트롤 층(헤더 띠·칩 행·pill)만 **글라스**(`bg-surface-glass/85 backdrop-blur-md border-b border-border`, 미지원 환경은 `@supports not (backdrop-filter: blur(1px))`에서 96% 불투명)로 한다. 모든 부유 표면은 1px 테두리 + 2단 그림자를 함께 쓴다 — 라이트 타일 위에서 그림자만으로는 경계가 약하고 다크에서는 그림자가 사라지기 때문이다. Apple HIG Materials는 두꺼운 material이 텍스트 대비에 낫고 글라스 효과는 "가장 중요한 기능 요소"에만 쓰라고 한다 ([Apple HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials)). 모바일 헤더는 지도 위 글라스 띠(56px) 안의 흰 solid 검색 pill(48px, `shadow-float-md`) + 바로 아래 가로 스크롤 칩 행, 데스크톱은 좌측 solid 패널 400px(`bg-background`, `border-r`)에 검색·서울 지금·칩·목록을 세로로 두고 헤더를 패널 상단으로 흡수한다. Kakao 저작권·로고는 시트가 하단을 덮으므로 `map.setCopyrightPosition(kakao.maps.CopyrightPosition.BOTTOMRIGHT, true)`로 우하단으로 옮기고 시트 peek 높이만큼 지도 하단 패딩을 주되, 영구히 가리거나 변색시키지 않는다 ([Kakao Maps 문서](https://apis.map.kakao.com/web/documentation/)).

다크모드는 **라이트 타일 + 다크 UI가 기본**이다. 근거는 Kakao 지도팀의 2026-09-21 공식 답변 "현재 SDK 내 다크모드 지원은 하고 있지 않으며"(권장 우회안도 제시 불가)와, 웹 JS SDK 문서에 스타일·테마 옵션이 없고 기본 지도 타입이 ROADMAP/SKYVIEW/HYBRID뿐이라는 점이다 ([devtalk 151789](https://devtalk.kakao.com/t/sdk-v2-mapstyle/151789)). 여기서 두 노트가 갈린다. 디자인 노트 §7은 "반전 금지, 운영 기본값으로 쓰지 않는다"(선택 실험 플래그에서 타일 레이어 한정 `brightness(0.78) …`만)라고 규칙을 세웠고, 인터랙션 노트 §7.3은 공식 샘플 페이지에서 **타일 레이어에만** `filter: invert(1) hue-rotate(180deg) brightness(.92) contrast(.88) saturate(.75)`를 걸면 레이블이 밝고 도로가 어두운 가독성 있는 다크 지도가 되며 **커스텀 오버레이 라벨과 Kakao 로고는 영향받지 않는다**는 것을 스크린샷으로 실측했고(`probe_out/dark_co_B_layer_invert.png`), 선택자 `.dark #kakaoMap div:has(> img[src*="/tile/"])`가 줌 전환 후에도 타일 레이어(1–2개)에만 일치함을 확인했다(실험 E5). 반면 단순 딤(`brightness(.55)`)은 탁한 회색 지도에 어두운 글자가 남아 가독성이 떨어졌다. **측정을 따르되 범위를 나눈다**: 기술적으로는 인터랙션 노트의 `:has()` 타일 한정 반전이 동작하고 로고를 건드리지 않는다는 것이 사실이므로 디자인 노트의 "딤만" 규칙은 폐기한다. 그러나 Kakao 약관상 타일 시각 변형 허용 범위와 로고 변색 정책은 **두 노트 모두 미확인**(포럼 질문 2건 미답변)이고 필터 합성 비용도 모바일에서 측정되지 않았으므로, 다크 지도는 **기본값이 아니라 사용자 설정의 opt-in 토글("지도도 어둡게")**로 넣고 `.dark[data-map-light]`에서 `filter: none`을 보장한다. 문제가 생기면 "지도는 항상 라이트" 폴백은 위험이 0이다 ([디자인 노트 §7](./design_direction_references.md), [인터랙션 조사 §7.3](./map_interaction_patterns_libraries.md)). 사람이 눈으로 비교할 캡처는 `D:\download\project\seoul-fit-fe\2026-10-11-map-interaction-research\index.html`(WSL `/mnt/d/download/project/seoul-fit-fe/…`)에 있다.

모션은 CSS transition/animation만으로 구현하고 길이·곡선은 Material 3 모션 토큰(short4 200ms, medium2 300ms; standard `(0.2,0,0,1)`, emphasized-decelerate `(0.05,0.7,0.1,1)`, emphasized-accelerate `(0.3,0,0.8,0.15)`)을, 원칙은 Apple HIG Motion("빈번한 상호작용에는 모션을 피하고, 취소 가능하게, Reduce Motion에서는 이동을 페이드로")을 따른다 ([material-web 모션 토큰](https://raw.githubusercontent.com/material-components/material-web/main/tokens/versions/v0_192/_md-sys-motion.scss), [Apple HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)). 규칙: 시트 열기 300ms enter / 닫기 200ms exit / 드래그 중 0 / 스냅 220ms standard(translateY만); 마커 선택 150/120ms scale+링; hover 120ms; 칩 토글 120ms 색만(**scale 금지** — 빈번한 상호작용); 목록 항목 진입은 첫 렌더·프리셋 전환 시에만 180ms stagger 30ms × 최대 8개; 다이얼로그 200/150ms opacity+scale(0.98→1); 토스트 200/150ms; 현재 위치 헤일로 2s 무한; 지도 panTo는 Kakao 기본, reduced-motion에서는 `setCenter`/`jump`. 제거 대상: `marker-bounce`, `marker-shake`, `pulse-warning`, 사이드바 설정 카드의 `hover:scale-[1.02] active:scale-[0.98]` + `group-hover:scale-110` + stagger `slideInRight`(`SideBar.tsx:166-182, 254-260`). 현재 전역 `prefers-reduced-motion`이 모든 animation/transition을 0.01ms로 강제하므로 페이드가 필요한 곳은 `.motion-keep-fade` 예외 클래스를 둔다. 스프링·제스처 물리 라이브러리는 **현 범위에서 불필요**하다 ([디자인 노트 §8](./design_direction_references.md)).

## 모바일 시트는 Base UI Drawer, 마커는 공식 클러스터러+CustomOverlay, Vaul·motion은 회피

인터랙션 조사는 후보 라이브러리를 헤드리스 Chrome for Testing 153 + Playwright-core 1.64 + React 19.3.0에서 **직접 실행·측정**했고(실험 E1–E11, 스크립트는 세션 스크래치패드 `scripts/`), 번들 크기는 esbuild `--bundle --minify`, React external, gzip -9로 쟀다. 실험 머신은 데스크톱 CPU의 소프트웨어 렌더링이라 절대 시간은 모바일보다 3–6배 낙관적일 수 있으며 **상대 비교로만** 써야 한다 ([인터랙션 조사 머리말](./map_interaction_patterns_libraries.md)).

### 바텀시트: 비모달 3단 스냅을 실측한 Base UI Drawer, 데스크톱은 Drawer 없이 `<aside>`

현재 `FacilityBottomSheet`는 `role='dialog' aria-modal='true'` + 전체 화면 오버레이(`fixed inset-0 bg-black/40 backdrop-blur-sm z-40`)라 **시트가 열려 있는 동안 지도를 조작할 수 없고**, React `onTouchStart/Move/End` 안의 `preventDefault()`는 React 17부터 passive라 무효이며("Keep `onTouchStart`, `onTouchMove`, and `onWheel` passive" — [React v17 changelog](https://legacy.reactjs.org/blog/2020/10/20/react-v17.html)), 높이는 `50vh/80vh`로 safe-area 처리가 없다. Material 3는 standard 시트가 "co-exist with the screen's main UI region and allow for simultaneously viewing and interacting with both regions"하고 modal만 scrim을 가진다고 구분하며 ([Material BottomSheet](https://github.com/material-components/material-components-android/blob/master/docs/components/BottomSheet.md)), Apple HIG는 nonmodal 시트·detent(large/medium)·grabber(탭으로 detent 순환, VoiceOver로 크기 조절)·스와이프 닫기를, HIG Maps는 "Keep the location on your map visible when displaying a place card"를 요구한다 ([Apple HIG Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets)). WCAG 2.2 SC 2.5.7은 드래그로 되는 모든 기능에 단일 포인터 대안을 요구하므로 핸들은 탭·버튼 대안이 필요하다 ([W3C 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)).

후보 비교에서 **Vaul 1.1.2(2024-12-14)**는 README가 "This repo is unmaintained."(2025-10-03)이고 이슈+PR 164건이 열려 있으며 `modal={false}`에서 포커스 트랩(#497)·body `pointer-events:none`(#492/#509) 버그가 남아 있고 수정 PR #580은 main에 병합됐지만 미배포(#647)다 ([vaul #630](https://github.com/emilkowalski/vaul/issues/630), [#647](https://github.com/emilkowalski/vaul/issues/647)). shadcn의 Radix 변형 `add drawer`는 지금도 Vaul을 설치하므로 수동 추가를 금지한다 ([shadcn Drawer (Radix)](https://ui.shadcn.com/docs/components/radix/drawer)). shadcn Sheet(Radix Dialog)는 스냅·드래그가 없고 항상 overlay를 렌더해 단독으로는 부적합하다 — 지도 코어 감사 §2.3이 "Radix Dialog + 스냅 자체 구현이 가장 저렴"이라고 본 것은 추론이고, 실측된 대안이 있으므로 Radix Dialog는 진짜 모달(로그아웃·경고·사이드바)에만 유지한다. **`@base-ui/react@1.9.0`(2026-10-09, MUI 팀, Drawer 도입 1.2.0=2026-02-12) Drawer**는 `modal: true | false | 'trap-focus'`, `snapPoints`(`'148px'`/0.5/1), `onOpenChange`의 이유(`'swipe'`, `'escape-key'`)와 `eventDetails.cancel()`, CSS 변수 `--drawer-snap-point-offset`/`--drawer-swipe-movement-y`, `data-starting-style/ending-style/swiping`을 제공한다 ([Base UI Drawer](https://base-ui.com/react/components/drawer)). 실험 E6(390×844, CDP 터치)에서 `modal={false}` + `disablePointerDismissal` + `snapPoints={['148px', 0.5, 1]}` 구성으로 **피크에서 지도 뒤 버튼 클릭이 2회 모두 반응**(지도 상호작용 유지), 바깥 `<input>` 포커스·입력 가능(트랩 없음), 핸들 드래그 −220px→0.5, −400px→1, 풀 스냅에서 콘텐츠 터치 스크롤 시 시트 불변, `scrollTop=0`에서 아래로 끌면 시트가 0.5로 내려가는 핸드오프, 피크에서 아래 스와이프는 기본 닫힘이지만 `reason==='swipe'`에서 `cancel()`하면 피크 유지, `escape-key`는 풀/하프에서 `cancel()`+`setSnap(peek)`로 한 단계 접기, 콘솔 경고 0건을 확인했다. 비모달인데도 기본값에서는 열린 직후 Popup이 포커스를 가져가 포커스 링이 보이므로 포인터로 마커를 고른 경우 `initialFocus={false}`를 준다(검증). Drawer 네임스페이스는 **38.7KB gz**이며 선택 이후에만 필요하므로 `next/dynamic`(Client Component 안에서 `ssr:false`)으로 lazy-load하고, **데스크톱(≥768px)은 Drawer 코드를 싣지 않고 좌측 `<aside aria-label>` 360–400px 패널**로 분기한다. 데모 CSS가 Tailwind v4 문법이라 3.4로 번역한 스케치(`data-[swiping]:transition-none`, `[transform:translateY(calc(var(--drawer-snap-point-offset)+var(--drawer-swipe-movement-y)))]` 등)는 모두 3.4.19에서 생성 확인됐다(E9) ([인터랙션 조사 §1](./map_interaction_patterns_libraries.md)).

행동 명세: 상태 3단 `peek`(핸들+제목+상태 배지+주요 액션 3개, 148–168px) → `half`(0.5: 운영시간·혼잡·추천 이유·대안) → `full`(1.0−16px). 초기 진입은 항상 peek, peek·half는 백드롭·포커스 트랩 없음, 풀에서만 약한 scrim(시각 처리만, `modal={false}` 유지). 닫기 사다리: Esc·뒤로가기 → full→peek → peek에서 한 번 더 = 선택 해제; 피크 아래 스와이프는 `cancel()`(우발 해제 방지); 지도 빈 곳 탭은 half/full이면 peek로, peek면 해제. 선택 시 마커가 시트에 가리지 않도록 `map.getProjection().containerPointFromCoords` + `panBy(dx,dy)`로 오프셋 이동(`revealAboveSheet` 스케치), 줌·내 위치 버튼·Kakao 로고는 `bottom: calc(var(--sheet-visible) + 12px)`. 핸들은 `<button aria-label="시설 정보 크기 조절" aria-expanded>`로 탭=단계 순환, ↑/↓=단계 이동, `touch-action: none`은 **핸들에만**(MDN의 줌 차단 경고), 본문은 `overscroll-behavior: contain`. `viewport = { viewportFit: 'cover' }`(Next 16.3.1 설치본 타입에 존재 확인) + `env(safe-area-inset-bottom)` + `dvh`. 탐색 패널(셸 D02)과 시설 상세는 **같은 Drawer 호스트의 두 콘텐츠**로 두어 시설 선택 시 상세가 탐색을 대체하고 닫으면 탐색 peek로 돌아가게 하는 것이 자연스럽다(이 보고서의 추론; 두 시트 동시 열림은 현재도 Provider가 막는다 — `FacilityProvider.tsx:574, 615-616`). 접근성 테스트 `PlaceExplorerPanel.accessibility.test.tsx`가 고정하는 region 이름 '장소 탐색 필터와 목록', combobox '최대 거리'·'지역 바로가기', 버튼 '내 생활'·'목록 닫기'(aria-expanded), 빈 상태 문구는 시트로 바꿔도 그대로 유지하면 통과한다. iOS Safari 러버밴딩·가상 키보드·VoiceOver는 **미검증**이다.

### 마커: 공식 MarkerClusterer에 CustomOverlay 객체를 넣는 조합이 5,000개에서도 DOM 139개

실측(E2, 479×693 지도, 서울 임의 분포)은 명확하다. 기본 `Marker`는 개당 DOM **5노드**(래퍼·img·투명 img·map·`<area href="javascript:void(0)" role="presentation" title=…>`)에 뷰포트 컬링이 없어 5,000개에서 DOM 25,143·334ms이고, `<area>`가 `tabIndex=0`이라 라이브 감사의 Tab 순서에서 본 "Kakao AREA"가 바로 그것이다. `CustomOverlay`는 뷰포트 컬링이 되지만(2,000개 중 76개만 DOM) 개별 `setMap`은 5,000개에서 **1,591ms**다. `MarkerClusterer`+기본 `Marker`는 113ms/DOM 248, **`MarkerClusterer`+`CustomOverlay` 객체**(HTML+SVG, grid 70)는 객체 생성 91ms + `addMarkers` 37ms에 DOM ≈139, 줌 재그리기 10ms로 가장 가볍다 — 단 문서에는 `Marker`만 명시돼 "동작하나 미문서화"다. 패닝 프레임 간격은 모든 구성에서 p95 16.7ms라 비용은 추가/재그리기/줌 시점에만 생긴다. `react-kakao-maps-sdk@1.2.2`는 React 19.3에서 정상 동작하고 5.6KB지만 `<MarkerClusterer>` 자식으로 넣은 `CustomOverlayMap`은 **클러스터링되지 않는다**(E8) → MapView 796줄 재작성 비용 대비 이득이 없어 **명령형 유지**하고, React 컴포넌트가 꼭 필요한 오버레이(선택 마커 등)는 `new CustomOverlay({content: div})` + `createPortal`로 만든 얇은 `KakaoOverlay` 훅(E8 검증)을 쓴다 ([인터랙션 조사 §2](./map_interaction_patterns_libraries.md), [Kakao MarkerClusterer](https://apis.map.kakao.com/web/documentation/)).

권장 구조는 2계층이다. 벌크 계층 = `CustomOverlay` 객체(카테고리 글리프·혼잡 링·따릉이 배지) → 공식 `MarkerClusterer({ averageCenter: true, gridSize: 64, minClusterSize: 2, minLevel: 4, disableClickZoom: true, calculator: [10, 50], styles, texts: n > 99 ? '99+' : n })`. 포커스 계층 = 클러스터러 밖 별도 오버레이(선택 시설·데스크톱 hover·추천 Top-N 배지·현재 위치)로 **선택 시설이 클러스터에 묻혀도 항상 보이게** 한다. `clusterclick`에서 레벨 ≤3 또는 크기 ≤6이면 클러스터 시트(목록), 아니면 `map.setBounds(cluster.getBounds(), 96, 48, 시트피크+24, 48)`로 영역 확대(HIG "클러스터는 줌인하면서 점진적으로 개별 POI를 드러낸다"). 현재 클러스터링은 **동일 좌표(소수 6자리) 그룹화**일 뿐이라(`useMapMarkers.ts:133, 157-164`) 1km 축척에서 마커 300개 중 183개만 클릭 가능했던 라이브 #14가 이것으로 해결된다. z-index 상수 `cluster 0 < marker 1 < hover 10 < selected 20 < me 30`은 래퍼에 적용되므로 `overlay.setZIndex()`로만 바꾸고 콘텐츠 내부 z-index·`!important`(`marker-animations.css:4-12`)는 삭제한다. 클러스터 DOM(`div`, role 없음)은 `clustered` 이벤트에서 `cluster.getClusterMarker().getContent()`에 `role="button"`·`tabindex=0`·`aria-label`을 주입하면 줌 후에도 재적용되고 Enter가 동작한다(E3 검증). 지도 키보드 조작은 `keyboardShortcuts: true`를 **생성자에 지정**하고 컨테이너 `tabindex=0` + `.focus()` 했을 때만 동작했다(생성 후 `setKeyboardShortcuts(true)`는 무반응, E4) — `useKakaoMap`은 이 옵션을 쓰지 않는다. 수백 개 마커를 Tab 순서에 넣지 않도록 오버레이 버튼은 `tabindex=-1`, 선택 마커만 `aria-current="true"` + 포커스 가능으로 하고, 키보드·스크린리더 경로는 목록·검색·시트로 둔다. 화면 `+/−` 줌 버튼(라이브 #23)은 `map.setLevel(level ∓ 1, { animate: true })`로 컨트롤 묶음에 넣는다. 미문서 조합이므로 배포 후 "클러스터 ≥1개 렌더" 스모크 테스트와 `Marker`+SVG data-URI `MarkerImage`(개당 2노드) 폴백 경로를 함께 준비한다.

리디자인하면서 **반드시 유지할 계약**(지도 코어 감사 §3.1): 마커 key `facility:${category}:${String(id)}` / `cluster:cluster-${lat},${lng}`(`useMapMarkers.ts:173-195`, 숫자 id 정규화·reconcile 테스트가 고정), 외부 문자열을 HTML에 넣을 때의 `escapeHtml`(현재 `marker.ts:5-16` module-private — export 하거나 `createElement`+`textContent`로 조립해 이스케이프를 불필요하게 만드는 쪽이 더 안전), 이벤트 계약(`role=button`·`tabIndex`·`aria-label`·Enter/Space), 앵커 `xAnchor 0.5 / yAnchor 1`(원형으로 바꾸면 0.5/0.5로 조정), `selectFacility(f, source)`의 `selection_source`와 `facility_detail_viewed`·`discovery_started`·`filter_applied`·`map_ready`·`geolocation_result` 등 트래킹 호출 위치, i18n 키(`map.*`, `facility.*`, `explorer.*`, `category.*`, `freshness.*`), 딥링크 `?lat&lng`·`?place=slug:id`, 시설 시트 액션(길찾기·공유·저장·예약·출처·대안·판단 요약)의 데이터 소스. `useMapMarkers.test.ts`의 mock은 `setMap/setPosition/setContent/setVisible`만 있으므로 `setZIndex`를 쓰면 mock을 보강한다. 콘텐츠 문자열이 바뀌면 요소를 통째로 교체(`:287-296`)하므로 선택·호버 상태는 content에 넣지 말고 `dataset`+CSS로 제어한다 ([지도 코어 감사 §2.2·§3](./code_audit_map_core.md)).

### 검색·칩·상태 피드백·다크모드·데모 폴백

**검색**은 인덱스 병합 버그(표 #1)를 먼저 고친 뒤 표시·키보드·ARIA만 **`cmdk@1.1.1`(`shouldFilter={false}`)**에 위임한다. cmdk는 React 19.3 개발 빌드에서 경고 0건, 입력에 `role="combobox" aria-expanded aria-controls aria-autocomplete="list"`, ↓ 입력 시 `aria-activedescendant`가 항목 id로 설정되고 **DOM 포커스는 입력에 유지**(APG 요구: "DOM focus remains on the combobox")되며 v1.1.1이 IME 조합 중 키 바인딩 이중 발동(#339)을 수정했다. 주의점도 실측됐다: `Command.Empty`는 `role="presentation"`(라이브 리전 아님)이라 결과 수를 별도 `role="status"`로 읽혀야 하고, `Command.List`의 기본 `aria-label`이 영어 "Suggestions"라 덮어써야 하며, `onKeyDown`에서 `e.nativeEvent.isComposing`이면 무시해 한글 조합 중 Enter 오작동을 막는다(현재 저장소에 `isComposing` 처리 0건). 증분은 Radix Dialog 공유 시 **≈4.2KB gz**. 초성·미완성 자모 매칭은 toss의 `es-hangul@2.4.0`(`getChoseong`+`disassemble` 1.9KB, 'ㅅㅇㅅ'→서울숲·서울시립미술관, '서울ㄷ'→서울도서관 검증)으로 하고 현재 `getMatchScore`의 초성 오탐은 "정확 일치 3 > 부분 일치 2 > 초성/자모 1" 점수로 대체한다. Radix에는 Combobox 프리미티브가 없고(`radix-ui@1.7.0` 구성 목록·npm 404 확인), Base UI Autocomplete는 50.4KB라 무겁다. 행동: 빈 입력+포커스는 최근 검색 ≤5 + 프리셋 바로가기, 입력 중에는 카테고리 그룹 헤딩 + 일치부 `<mark>` 강조(NN/g: 이미 입력한 글자를 굵게 하면 반복 강조), Esc 1회=팝업 닫기·2회=입력 비우기, 0건은 Empty + CTA(필터 초기화/현재 지도에서 다시 검색), 로딩 중에는 Empty를 먼저 보여주지 않는다 ([APG Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [NN/g Site Search Suggestions](https://www.nngroup.com/articles/site-search-suggestions/), [인터랙션 조사 §3](./map_interaction_patterns_libraries.md)). 의존성을 더하고 싶지 않다면 현행 구조에 `aria-activedescendant`·실제 `aria-selected`·`isComposing` 가드·결과 수 status·`<mark>`를 보강하는 무의존 경로도 가능하다.

**칩**은 두 줄 구조다: 프리셋 6개는 "상황" 단일 선택(재탭 해제가 유효 상태이므로 라디오보다 `aria-pressed` 토글이 적합), 카테고리 8개는 다중 선택 + 개수. iPhone 세그먼트 컨트롤 권장 한도는 "no more than about five segments on iPhone"이라 6개 프리셋은 세그먼트가 아니라 가로 스크롤 칩으로 간다 ([Apple HIG Segmented controls](https://developer.apple.com/design/human-interface-guidelines/segmented-controls)). 라벨은 상태와 무관하게 고정("공원 132"), 선택 표현은 색 + 체크 아이콘, 높이 36–40px, `overflow-x-auto overscroll-x-contain` + 가장자리 페이드 마스크 + 선택 칩 `scrollIntoView({inline:'center'})`(라이브 #19의 잘림·힌트 부재 해결), 결과 수 요약 줄 "지도 안 128곳 · 필터 3개"를 `role="status"` 1곳에서만(300ms 디바운스), 필터가 하나라도 걸리면 "모두 지우기" 노출. 가로 필터 툴바는 6–8종을 넘으면 문제가 되므로(Baymard) 8개 카테고리는 경계선이며 탐색 패널에 전체 목록을 병행한다 ([Baymard](https://baymard.com/blog/horizontal-filtering-sorting-design)). 스케치 클래스(`aria-[pressed=true]:border-primary`, `[mask-image:linear-gradient(...)]`, `snap-x`)는 3.4.19에서 생성 확인됐다.

**상태 피드백**은 NN/g 규칙을 따른다: 스켈레톤은 "exclusively for full-page loads"이고 1초 미만이면 불필요, 10초 초과면 진행 막대이며 "they do not replace performance-optimization efforts"다 ([NN/g Skeleton Screens](https://www.nngroup.com/articles/skeleton-screens/)). 그래서 지도 SDK·타일 첫 로딩만 지도 형태 플레이스홀더(회색 타일 격자 + 컨트롤 자리 + "지도를 불러오는 중", `aria-busy`, 200ms 지연 후 표시·≥400ms 유지)로, 목록·추천 첫 로딩은 높이 고정 카드 스켈레톤 3–5행, 시트 안 날씨·혼잡·도착정보는 모듈 단위 인라인 문구, 지도 이동·필터 변경 후 1초 미만 재조회는 기존 결과 유지 + 요약 줄 미세 스피너(stale-while-revalidate), 0건은 상태 문구 + CTA 2개다. **토스트는 `sonner@2.0.8`(9.6KB)로 교체**한다: 실측 DOM이 `section[aria-live="polite"][aria-relevant="additions text"]`이고 `prefers-reduced-motion` CSS를 내장하며 콘솔 경고 0건이지만 기본 라벨 "Notifications alt+T"가 영어라 `containerAriaLabel="알림"`과 `closeButtonAriaLabel`을 지정한다. 현행 `src/shared/lib/utils/toast.ts`는 구현이 둘(우하단 class `toast` vs 상단 중앙 `showToast`), `role`/`aria-live` 없음(스크린리더 미공지), 흰 글씨 on `#10b981` **2.54:1**·`#ef4444` 3.76·`#3b82f6` 3.68·`#f59e0b` **2.15:1**로 전부 AA 미달, `zIndex 9999`, import 시점 `<style>` 주입이다; `toast.test.ts`가 `showToast` 계약을 고정하므로 교체 시 테스트도 교체한다. 복구가 필요한 오류(위치 거부·지도 실패·API 502)는 자동 소멸하는 토스트가 아니라 **인라인 배너 + 복구 버튼**이다. **위치 권한**은 Lighthouse `geolocation-on-start`("Always request geolocation permission after a user action, not on page load", "Assume users won't give you their locations")에 따라 로드 시 자동 프롬프트를 없애고 "내 위치" 버튼에서만 요청하며, `navigator.permissions.query({name:'geolocation'})`가 `denied`면 프롬프트 없이 안내, 첫 요청은 `enableHighAccuracy:false, maximumAge: 5분`으로 빠르게, 코드별(1 denied / 2 unavailable / 3 timeout) 문구 분기, `PermissionStatus.onchange`로 설정에서 켜면 자동 복구, 거부 상태는 "위치 권한이 꺼져 있어 서울시청 주변을 보여드려요 · [내 위치 켜는 방법] [서울시청 유지]" 배너로 **오류가 아닌 정상 경로**로 다룬다 ([Chrome geolocation-on-start](https://developer.chrome.com/docs/lighthouse/best-practices/geolocation-on-start), [MDN Permissions API](https://developer.mozilla.org/en-US/docs/Web/API/Permissions_API)). 신선도 배지는 `<time dateTime>` + `Intl.RelativeTimeFormat('ko', {numeric:'auto'})`("3분 전", "어제")로 통일하되 `(0,'minute')`이 "현재 분"을 돌려주므로(node 24 검증) 1분 미만은 "방금"으로 별도 처리하고, 현재 세 벌인 신선도 라벨(`messages.ts:80-83` '실시간/최근 갱신/갱신 지연/기준 시각 미확인', `live-data.ts:11-16` '정상 갱신…', `provenance.ts:24-32`)과 다른 임계값(live-data 15분/60분, provenance 15분/24시간)을 `freshness.*` 키와 공유 상수로 합친다 ([지도 코어 감사 D-18·§2.5](./code_audit_map_core.md), [인터랙션 조사 §5](./map_interaction_patterns_libraries.md)).

**다크모드**는 `next-themes@0.4.6`(1.5KB, `attribute="class"`가 `darkMode: ['class']`에 바로 맞음, FOUC 없음, 탭 동기화)을 쓰되 알려진 비용을 감수한다: React 19.2+ 개발 빌드에서 `ThemeProvider`가 "Encountered a script tag while rendering React component…" 콘솔 에러를 내는 것이 실측 재현됐고(이슈 #385/#387/#397, 기능은 정상, 수정 `ThemeScript` export는 main에만 있고 미배포) ([next-themes #385](https://github.com/pacocoursey/next-themes/issues/385)). `<html suppressHydrationWarning>`, `viewport.colorScheme: 'light dark'`, `themeColor` 배열, 토글은 마운트 후에만 렌더(시스템/라이트/다크 3단, 라벨 고정). 대안은 서버 컴포넌트 `<head>` 인라인 스크립트 + `useSyncExternalStore` 약 40줄 직접 구현(경고 경로 회피는 미검증). 진짜 작업량은 라이브러리가 아니라 **하드코딩 색 577곳/28파일(`dark:` 변형을 쓰는 파일은 4개)**의 토큰 이행이며, 이는 앞 절의 토큰 작업과 같은 일이다. **데모 폴백**: 잘못된 앱키는 SDK가 HTTP 401 JSON(`AccessDeniedError`)을 돌려주고 `<script>`의 `onerror`가 발화하며 DNS 실패도 `onerror`다(검증). 현재 `useKakaoMap`은 실패한 `<script>` 태그를 제거하지 않아 재시도 시 같은 실패 태그를 다시 기다리므로, 로더는 `script[data-kakao-sdk]`를 제거 후 재삽입하고 8초 타임아웃 + 1s/3s/9s 백오프 3회 + 수동 버튼으로 바꾼다. 실패 시 정적 미리보기(`public/map-fallback.svg`, "실제 지도를 불러오지 못했어요" 캡션으로 정적임을 명시) + "목록으로 보기"(시설 데이터·시트는 SDK와 독립이라 지도 없이 동작) + 원인별 문구. 등록 도메인 밖(프리뷰 URL·다른 포트)에서는 지도가 실패할 수 있다는 Kakao 가이드("등록된 사이트 도메인에서만 지도API를 사용할 수 있기 때문에 반드시 등록해주세요")도 폴백의 근거다 ([Kakao 가이드](https://apis.map.kakao.com/web/guide/)). 프리셋 딥링크(`?preset=rainy_day` 등)는 현재 `MapView.tsx:180-195`가 `lat/lng`만 처리하므로 **신규 구현**이다 ([인터랙션 조사 §7·§8](./map_interaction_patterns_libraries.md)).

성능 가드레일은 라이브러리보다 서드파티 지도(SDK 37.4KB gz + 타일 PNG 장당 ≈21.8KB)·마커 DOM·검색 인덱스 871KB·폰트 선택이 병목이라는 사실에서 나온다: `dapi.kakao.com`·`t1.kakaocdn.net`·`mts.kakaocdn.net` preconnect, `autoload=false` + `libraries=clusterer`, 지도 컨테이너 높이 CSS 고정(CLS), 모바일 시트·검색 패널·활동 계획/알림 패널 `next/dynamic`, 화면 내 마커 유래 DOM 상한 ≈300, 필터 변경 시 전체 재생성 금지(diff 갱신, `addMarkers(…, true)` 후 `redraw()` 1회), 시트는 `transform`만 애니메이션하고 드래그 중에만 `will-change`, 패널·시트는 지도 컨테이너 크기를 바꾸지 않는 오버레이로 두어 `relayout()`·타일 재요청 회피, 검색 인덱스는 서버 검색 API 또는 지연 로드, 지하철 중복 요청 제거. 현실적 목표는 Lighthouse 모바일 ≥85(스트레치 90), LCP ≤2.5s, CLS ≤0.1이다 ([web.dev Core Web Vitals](https://web.dev/articles/vitals)).

평가 기준을 직접 밝힌 한국 조직의 1차 자료는 토스뿐이다. 토스 Head of Frontend는 2025-04-08 글에서 이력서 없이 공개 저장소 링크 하나로 지원받으며 "저희 프론트엔드 리더들은 오직 코드를 기준으로 평가할게요"라고 썼고, 제출 가이드는 **모듈화·코드 품질 / 명확한 디렉토리 구조 / TypeScript를 정확하게 / 제품의 완성도(성능 또는 사용 경험) / 읽기 쉬운 커밋·PR 단위 / 화려한 기술보다 본질적인 고민 / 무엇을 구현하는지 알 수 있는 README**를 열거한다 ([토스 테크](https://toss.tech/article/frontend-apply-without-resume)). 카카오 채용 FAQ는 포트폴리오를 URL로 내도 되지만 "서류 검토 전 URL이 변경되거나 사라질 경우 포트폴리오 확인이 불가"라고 경고하고 ([카카오 영입 FAQ](https://careers.kakao.com/faq)), 당근은 PDF를 권장하며 웹 링크는 파일 안에 넣으라고 한다 ([당근 채용 FAQ](https://careers.daangn.com/faq/%EC%A7%80%EC%9B%90-%EA%B4%80%EB%A0%A8/)). 즉 평가자는 PDF → 라이브 URL → 저장소의 서로 다른 입구로 들어오며, 세 곳 모두 60초 안에 "무엇이고, 왜 이렇게 만들었고, 실제로 도는가"가 읽혀야 한다. 2026년 자료는 AI가 만든 결과물이 흔해진 만큼 "How the candidate explains a decision, not just what they decided"가 신호라고 덧붙인다 ([SocialTalent](https://www.socialtalent.com/?p=96405)). 사용자·트래픽이 없는 것은 약점이 아니다 — 토스 기준에 사용자 수는 없고, 가짜 지표는 면접 꼬리질문에서 가장 쉽게 무너진다 ([포트폴리오 조사 §1·§6](./portfolio_presentation.md)). 서울핏은 FSD형 구조·`strict: true`·Jest 테스트·접근성 체크리스트·불변 릴리스·관측성 문서·BACKLOG의 트레이드오프 기록이라는 **재료를 이미 갖고 있다**; 문제는 그 재료가 첫 화면(README·URL·PDF)에 올라와 있지 않다는 것이다.

**브랜드·메타 자산**은 S 노력으로 끝난다. 현재 공개 `<head>`에는 `favicon.ico`와 OG/Twitter 태그만 있고 `/icon.svg`·`/apple-touch-icon.png`·`/manifest.webmanifest`·`/about`·`/privacy`·`/terms`가 모두 404이며, 헤더 로고(핀 글리프 inline SVG, `Header.tsx:345-368`)와 `public/assets/logo.svg`(참조 0)와 OG 이미지의 "S" 타일(`app/opengraph-image.tsx:28-43`)이 **서로 다른 세 로고**이고, 탭 제목은 "서울 공공시설 지도 | Seoul Fit"인데 공유 카드는 "Seoul Fit | 서울 공공시설 지도"로 순서가 뒤집혀 있다(셸 D26). 최소 세트는 `favicon.ico`(32) + `app/icon.svg` + `app/apple-icon.png`(180, 여백 ≈20px) + `app/manifest.ts`(192/512/maskable) 다섯 파일이며 ([Evil Martians](https://evilmartians.com/chronicles/how-to-favicon-in-2021-six-files-that-fit-most-needs), [Next.js app-icons](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/app-icons)), PWA는 **manifest까지만** — Next 문서가 설치에 오프라인이 필요 없다고 명시하고 라이브 데이터 의존 앱에 오프라인 가치가 낮다 ([Next.js PWA](https://nextjs.org/docs/app/guides/progressive-web-apps)). 로고는 단일 `Logo.tsx`로 헤더·OG·파비콘이 공유하고 헤더에 "Seoul Fit" 워드마크를 넣으며, OG는 텍스트 카드(1200×630, 66KB) 대신 실제 제품 화면(카카오 로고 포함) + 한 줄 가치 + 도메인으로 바꾸되 `next/og`가 한글 글리프를 런타임에 외부에서 동적 로드하므로(`loadDynamicAsset`) 파드 egress가 막히면 □□가 될 위험이 있어 본문과 같은 Pretendard 파일을 `fs.readFile`로 `fonts` 옵션에 넘긴다(셸 D27). `viewport.themeColor`는 브랜드 색으로, `<title>`은 전 페이지 "… | Seoul Fit"으로 통일한다. 카카오 로그인·분석을 쓰는 서비스이므로 짧은 개인정보 처리방침·이용약관·데이터 출처 페이지 + 푸터 링크는 신뢰 신호이나 법적 필요성은 소유자 판단이다 ([포트폴리오 조사 §4](./portfolio_presentation.md)).

**품질 지표는 측정 조건과 함께** 게시한다. 직접 측정한 베이스라인(2026-10-10T16:5x Z, Lighthouse 13.5.0, headless Chrome for Testing 149, WSL2, `/`)은 데스크톱 **91/95/88/100**(FCP 0.5s, LCP 1.9s, TBT 0ms, CLS 0.005), 모바일 기본 시뮬레이션 throttling 성능 **56과 45**(LCP 8.1/7.5s, TBT 790/3,380ms), 모바일 `--throttling-method=provided` **100**(LCP 1.1s)이다. 모바일 LCP 요소는 지도 컨테이너 `div#kakaoMap`이고 관측 LCP 분해는 TTFB 373ms + 리소스 지연 546ms + 렌더 70ms ≈ 1.0s로 시뮬레이션 8.1s와 크게 다르므로, 단일 숫자가 아니라 "조건별 범위 + 해석"을 게시해야 한다. Lighthouse 문서 스스로 점수를 "a distribution of scores, rather than a single number"로 보라고 하고, 접근성 점수는 자동 audit의 가중 평균일 뿐 수동 audit을 제외하며 ([Lighthouse performance scoring](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring), [accessibility scoring](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)), Deque 연구는 자동 테스트가 접근성 이슈의 57%(건수 기준)만 잡는다고 보고한다 ([Deque](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues/)). 실패 audit 중 자체 수정 가능한 세 건 — `color-contrast`(칩 흰 글자), `heading-order`(h3 "짧은 활동 계획"), `label-content-name-mismatch`(칩 aria-label) — 과 Best Practices 두 건(`errors-in-console` 위치 거부 로그, `geolocation-on-start`)은 앞 절의 수정으로 해소되고, `presentation-role-conflict`(카카오 SDK의 `<area role="presentation">`)와 `image-size-responsive`(SDK 투명 gif)는 "서드파티 요소"로 한계에 기록한다. 게시 형식은 `지표 | 값 | 측정일 | 도구·버전·조건 | 한계/해석`이며 n≥5 중앙값과 범위를 쓰고 상세 JSON은 `docs/quality/lighthouse-YYYY-MM-DD.md`로 커밋한다. 테스트 수는 정적 grep 값(262)이 아니라 Jest 요약 줄(예: 감사에서 42 suites / 276 tests 통과)과 실행 명령을 그대로 적고, 타입은 `strict: true` + `npm run type-check` 통과 한 줄, 번들은 `npx next analyze --output` 스냅샷을 날짜와 함께 둔다 ([Next.js package bundling](https://nextjs.org/docs/app/guides/package-bundling)). 접근성은 W3C WAI 성명서 형식("WCAG 2.2 AA를 목표로 점검했고, 자동 검사 결과와 알려진 한계는 아래와 같습니다")으로 쓰고 **준수(conformance)를 단언하지 않는다** ([W3C WAI Accessibility Statements](https://www.w3.org/WAI/planning/statements/)). 하지 말 것: 최고점만 게시, "WCAG 준수·접근성 완벽", MAU·방문자·후기, 목업을 라이브처럼 표기, 규칙 기반 추천을 "AI 추천"으로 포장, 공공누리·카카오 고지 생략. "공모전 이후 실사용자 없음, 포트폴리오 목적 운영"이라고 쓰는 편이 신뢰를 지킨다. ADR은 단일 replica·프로세스 내 캐시, 규칙 기반 점수 + 근거 표시, SSR 공개 페이지 + 클라이언트 지도, 불변 digest 릴리스, 그리고 이번 Tailwind 3.4 유지 결정 — 다섯 건을 `docs/decisions/`에 소유자 devkit의 `decision-records.md` 형식으로 남긴다 ([포트폴리오 조사 §5·§7](./portfolio_presentation.md)).

## 결론

이 조사가 바꾼 이해는 두 가지다. 첫째, 서울핏의 "덜 멋짐"은 시각 언어의 부재가 아니라 **"데이터 없음" 톤**에서 온다 — 502로 죽은 차별점, 시청역만 반복하는 추천, 세 번씩 "미확인"을 설명하는 판단 카드, 빈 첫 화면이 합쳐져 기능이 많을수록 빈약함이 더 드러난다. 그래서 색·폰트·마커 해부도는 2단계이고, 1단계의 본질은 상태 모델(로딩·부분 실패·권한 거부·빈 결과·stale)을 UI에 연결해 "작동 중인 제품"으로 읽히게 만드는 일이다. 디자인 방향을 유틸리티 골격으로 고정한 것도 같은 이유다: 지도 서비스에서 신뢰감은 장식이 아니라 상태의 정직함에서 나오고, 9색 카테고리가 CVD에서 분리되지 않는다는 측정은 "색은 보조, 글리프·라벨·숫자가 1차"라는 원칙을 디자인 전체에 강제한다.

둘째, 이번 종합에서 노트 간 결론이 갈린 세 지점(시트 등장 애니메이션 수단, 마커 z-order, 다크 지도)은 모두 **추론이 측정에 졌다**. `tw-animate-css`는 두 독립 측정에서 0건, 마커 `style.zIndex`는 실측에서 무효, 다크 타일 필터는 기술적으로 동작하되 약관이 미확인이라 opt-in으로 갈렸다. 이 패턴은 구현 중에도 반복될 것이다 — Base UI Drawer의 iOS 거동, Pretendard 조각의 번들 처리, 미문서 클러스터러 조합처럼 "문서에 없거나 헤드리스로만 본" 것은 전부 구현 시 한 번의 측정(스모크 테스트·빌드 산출 grep·실기기 캡처)으로 닫아야 하며, 닫지 못한 것은 README의 "알려진 한계"에 그대로 적는 것이 포트폴리오의 설득력을 만든다. 평가자가 가중하는 것은 완벽한 점수가 아니라 결정을 설명하는 증거이므로, 이 계획의 산출물 중 가장 값싼 것(ADR 5건, 측정 조건이 붙은 품질 표, 리뷰어 코드 지도)이 가장 큰 차별점이 될 가능성이 높다.
